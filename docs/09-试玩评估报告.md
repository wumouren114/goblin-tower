# 试玩评估报告 · 重做 vs 迭代的判断依据

> 评估对象：《残响高塔 · ECHO SPIRE》v4.6（工作区当前状态）
> 评估方式：无头浏览器实机运行 + 源码审查 + 整局蒙特卡洛模拟
> 评估日期：2026-11-01

---

## 0. 结论先行

**不要推倒重来，也不要继续微调。应该"保留骨架、替换心脏"——原地重建战斗、构筑、场景三层。**

这不是折中，而是三条独立证据指向的同一个答案：

| 判断 | 支持证据 | 代价 |
| --- | --- | --- |
| 全部重写 ❌ | 25,641 行 TypeScript 里约 70% 与"可玩性"无关（渲染批处理、HUD、存档、商店、背包、音频合成、美术归一化、单文件打包） | 2–3 个月重新长一遍同样的骨架，可玩性收益 ≈ 0 |
| 继续调参 ❌ | v3 → v4.6 已经迭代六轮，全部是数值、加内容、加觉醒，**可玩性没有质变** | 已经在发生，且被证明边际收益趋零 |
| 原地重建 ✅ | 问题集中在三个模块（构筑 / 战斗 / 场景），且都是**数据模型级**缺陷，改不了了修补 | 重写约 20–30% 代码，骨架全部复用 |

你原话里的"重新设计框架底层逻辑、战斗系统、场景美术"——**这本身就是原地重建**。所以真正的选择不是"重做 or 改"，而是**重做的粒度**。

| 场景 | 9 个主题，**几何结构完全相同**（一片方形空地 + 换色换贴图） | 每个生态有独立的关卡语法 |

### 2.3 平衡数据（我自己跑的，不是 README 引用）

```
简单    100% 通关 × 3 角色    平均清层 23.1s
普通    100% 通关 × 3 角色    平均清层 31.2s
困难     94.5%（睦）/ 100%（丛雨）/ 98%（肥鱼）    平均清层 26s
```

**结论：会走位的玩家几乎不会输。** 困难难度三局通关两局半以上，而玩家的操作只有"移动"。

> 需要说明的是，`simulate.mjs` 模型不含走位与地形遮挡，绝对通关率偏乐观（`docs/06` §8.2 自己注明了这点）。站桩实测确实会死人：普通第 10 层站桩满血，困难第 15 层站桩 17 秒阵亡。
>
> 但这恰恰暴露了问题所在——**威胁只惩罚"不动的玩家"，不奖励"会走的玩家"**。躲开只需要按住方向键，不需要判断、不需要取舍、不需要技术。死亡是"耗死"，不是"被击败"。这比"不会死"更糟：它既没有紧张感，也没有学习曲线。

## 3. 试玩发现

### 3.1 战斗：反馈做得不错，但**没有需要技术的时刻**

可操作的东西只有三样：左键普攻（**自动索敌，按住不连发**）、右键技能（充能制）、Shift 冲刺（带无敌帧）。

- 普攻自动锁定最近敌人 → 站位、朝向、瞄准全部被系统接管，玩家只负责"走位 + 准时按技能"。
- 冲刺有无敌帧，但没有任何机制**要求**你用它（威胁靠按住方向键就能规避）。
- 四个伤害入口（`combat.ts` 第 535 / 574 / 724 / 1058 行）都是 `伤害 = 基础 × 暴击倍率` 一条公式，没有元素、状态、护甲交互、部位判定。

结果：手感（屏震、飘字、粒子、音效）是**及格甚至不错的**，但**可操作空间**很窄。割草游戏的核心快感来自"看起来危险但被我化解"，现在是"看起来热闹但不会受伤"。

### 3.2 构筑：这是全篇最严重的问题

背包界面把问题暴露得最彻底——右侧"已获卡牌汇总"是一列纯数字：

```
魔力 +56   耐力 +32   智力 +12   生命上限 +25   移速 +0.25
充能上限 0  充能效率 0   闪避 0   减伤 0   暴击率 0
```

**15 张卡池（10 增益 + 5 技能）里，没有一张能改变"你怎么打"。** 它们只改变"数字跳得多大"。

唯一的机制层是 v4.6 的觉醒（18 个），但单局只能拿 2 个、每个 3 级，且被风格锁死。9 套风格 × 2 觉醒 = 18 种组合，听起来不少，实际上：
- 同一个风格里，两个觉醒是"唯一解"——先拿哪个、之后深化哪个，最优解清晰到几乎不需要思考。
- 觉醒不产生交互（共鸣标记 × 余音音场 = 两个独立乘区），没有"这两个凑一起会爆炸"的 Build 时刻。

**根因是数据模型**：`stat += value` 这个 schema 表达不了"当 X 时 Y 变成 Z"。所以无论再往里加 20 张卡，都还是同一个扁平线性堆叠。**这是必须换 schema 的地方，不是调数值的地方。**

### 3.3 场景：9 个主题，1 个关卡

同一个方形竞技场，四面墙边的刷新点，中间一个祭坛。主题差异 = 地板颜色 + 墙面贴图 + 环境光。

只有装饰性道具（木桶、箱子、柱子、水晶），没有**掩体、通道、高低差、危险区域**。

这意味着：**难度的唯一变量是数值。** 没有地形，就没有"把怪引到窄口""用柱子卡住冲锋""绕祭坛风筝"这类操作空间。这也是为什么后期只能靠"小怪移速 ×1.9""蛮兵冲撞"来制造压力——在没有地形的空地上，只能靠增加追人能力。

### 3.4 可读性：实机截图暴露的两个硬伤

- **玩家角色会被怪堆淹没**。第 15 层同屏 30 只时，你自己的角色完全看不见（`shots/eval/hard15.png`）。
- **预警文字会重叠成一坨**。多条"蓄力冲撞 / 震地"同时触发时，屏幕右下的黄字叠在一起完全不可读（同上）。

HUD 本身做得很好——信息层级清楚、数值齐备、左下角资源条（节拍/剑意/泡泡）设计得比很多商业 demo 都干净。问题在于**战斗现场的可读性**。

### 3.5 反馈循环：缺失"风险—回报"

无倒计时、无失败压力、无资源取舍。玩家每一步决策的正确性都不影响能否过关，只影响过得多快。

于是整局的真实体验是：**清点任务**。清 40 只 → 选一张卡 → 走一条隧道 → 再清 40 只。8–12 分钟里没有一次"我要不要赌一把"。

## 5. 根因：三个"扁平"

你的直觉"提示词设计得太简陋"其实抓到了表层。真实因果链是：

```
提示词只写"做什么"，不写"约束 + 验收标准"
        ↓
每个系统都做出了"能跑的最小实现"（自动索敌的战斗、加数值的卡、换色的场景）
        ↓
三个系统各自扁平，且互相之间不产生耦合
        ↓
玩家没有任何"决策"可做 → 只有操作，没有选择
        ↓
可玩性差
```

三个扁平具体是：

1. **构筑扁平**：`属性 += 常数` 的数据模型 → 表达不了条件、触发、联动。
2. **敌人扁平**：4 种怪共用"追击 + 一招"的 AI 骨架 → 没有威胁类型（远程压制 / 封路 / 冲锋线 / 召唤 / 自爆）的分工。
3. **空间扁平**：一片空地 → 难度只能堆数值，操作空间的上限被几何结构锁死。

**这三个"扁平"直接对应新框架必须重写的三个模块。** 也正因为是"扁平"而不是"缺功能"，加内容永远补不上——加 20 张卡还是 20 张 `+数值`。

### 顺带：工作台本身也有同一个病

`肉鸽爬塔AI提示词工作台.html` 有 9 个阶段、约 **155 个任务位**，覆盖极全。但它每一行只有：
`[任务名]` + `[空白提示词框]` + `[产出记录]`。

它缺的正是"约束与验收标准"——所以填出来的提示词必然停在"帮我设计战斗系统"这种粒度，而 agent 对这种输入只能还你一个最小实现。**工作台的结构问题和工作台产出物的问题是同一个问题。**

## 6. 建议的重写边界

### 必须保留（不要碰）

| 模块 | 理由 |
| --- | --- |
| Vite + TS strict + three.js 技术栈 | 稳定、零依赖负担 |
| `art/billboardBatch / groundBatch / shadowBatch` 渲染批处理 | 性能底座，跟玩法无关 |
| `balance.json` 单一数值源 + 访问器模式 | 模式对，只需扩 schema |
| `sim/` 模拟管线 + 4 套 smoke | 这是本项目最值钱的东西——能自动验证 |
| 三槽存档 / 层快照重试 / 单文件打包 | 工程护城河 |
| `scripts/art-normalize.py` + `atlasImport` 美术管线 | 换美术方向时直接复用 |
| `scripts/make-audio.mjs` 音频合成 | 同上 |
| HUD 框架、商店/隧道/背包的界面骨架 | 结构对，换皮即可 |
| 三角色身份 + 五维面板 | 角色可以留，战斗表现重做 |

### 必须重写（schema 级，不是修改）

| 模块 | 从 | 到 | 预估量 |
| --- | --- | --- | --- |
| **构筑引擎** | `stat += value` | `Effect / Trigger / Condition` 数据模型 + 词条引擎（事件钩子：命中/击杀/受伤/施法/暴击/闪避） | 800–1200 行新模块 |
| **战斗内核** | 1 普攻（自动索敌）+ 1 技能 + 1 冲刺 | 明确的"操作深度"契约：普攻 / 重击（蓄力）/ 闪避取消 / 技能 / 资源条；命中判定分层（普通/破防/背击） | 重写 `combat.ts` + `attack.ts` |
| **敌人 AI** | 追击 + 1 招 | 行为节点框架 + 5 类威胁原型（远程压制、封路、冲锋线、召唤、自爆） | 新框架 + 每类 1–2 个实例 |
| **场景/关卡** | 单片方形空地 | 有结构的竞技场：掩体、通道、危险区、可交互物；主题差异从"换色"变成"几何 + 光照 + 音景"整体差异 | 重写 `floor.ts` 布局层 |
| **可读性层** | 无 | 玩家描边/遮挡透明化、预警合并显示、伤害数字聚合 | 新模块 |

### 需要新建（现在完全没有）

- **波次编排器（wave director）**：替代"刷怪配额"。按威胁原型组合出有节奏的波次，而不是匀速刷 40 只。
- **事件/抉择层**：风险房、诅咒、代价换收益——制造 risk/reward，这是当前最缺的一层。
- **失败压力设计**：不是加倒计时，而是让"走位失误"真的会死。

## 7. 执行建议：垂直切片，不要横向铺

**不要**一次性铺 9 层 18 觉醒。**先做一个切片证明手感成立**：

> **切片范围**：1 个角色（建议丛雨，近战最能验证打击感）+ 1 个场景（做到"能卖"的标准）+ 3 层 + 1 个 Boss + 30 张新卡。

| 阶段 | 内容 | 验收标准 | 预估 |
| --- | --- | --- | --- |
| P0 | 冻结当前版本为 `v4.6-baseline` tag | 随时能跑起来对照 | 0.5 天 |
| P1 | 战斗内核原型（灰盒，不接美术） | 新战斗集下，**困难难度通关率 30–60%**（现在 94.5%），且玩家能说清"我为什么死了" | 3–5 天 |
| P2 | 构筑引擎 + 30 张词条卡 | 能玩出 ≥3 条可辨认、胜率接近的 Build 路线 | 1–2 周 |
| P3 | 场景美术重做（先做 1 个主题） | 该主题达到"截图能当宣传图"的标准 | 1–2 周 |
| P4 | 内容量产 + 平衡 | 3 场景 × 5 层，模拟通关率 35–55% | 2–3 周 |

**P1 的验收标准是关键**：如果新战斗系统的困难通关率还在 90% 以上，说明"操作"仍然不影响胜负，那就还没做对，不要往下走。

## 8. 风险

| 风险 | 应对 |
| --- | --- |
| 重写战斗后手感变差（现有反馈层是加分项） | 重写的是**判定与决策层**，屏震/粒子/飘字/音效整套反馈全部保留复用 |
| 构筑引擎过度设计 | 先实现 5 个钩子（命中/击杀/受伤/施法/暴击），30 张卡验证够用再扩 |
| 场景重写拖垮性能 | 现有批处理架构不动，只换布局与道具密度 |
| 数值重置后 sim 管线失效 | `simulate.mjs` 与 `balance.json` schema 同步升级，P1 就必须跑通 |
| 美术方向反复 | P3 之前不接美术，灰盒验证玩法；题材/风格先定 1 页纸再出图 |

---

## 9. 一句话总结

**这个项目的工程能力（8/10）远高于它的游戏性（4.4/10）。重做工程是浪费，继续调数值是徒劳；把"构筑 / 战斗 / 场景"三个扁平结构换成有深度模型，其余全部 reuse——这是唯一性价比正确的路线。**
